# Momentum — твой день, твой ритм, твой прогресс

PWA-приложение для привычек, тренировок и планирования дня. Основное хранилище —
IndexedDB (Dexie) на устройстве; при желании и наличии кабинета данные уходят в
Supabase и переносятся на другие устройства. Без кабинета приложение работает
полностью локально, и ничего никуда не отправляется.

## Возможности

- **Привычки (День)** — отмечайте привычки кольцом, перетаскивайте между
  категориями и подкатегориями (drag & drop, `@dnd-kit`), считайте серии (streak),
  пропускайте дни с причиной. Тепловая карта + мини-графики.
- **Тренировки** — план на неделю, карточки по дням: клик по карточке открывает
  редактирование, меню карточки даёт «Создать копию», отмену тренировки с
  восстановлением из тоста и постоянное удаление. Упражнения (подходы/повторы/вес,
  время отдыха в секундах, объём в тоннах; для кардио — угол наклона, скорость,
  расстояние и длительность), шаблоны, «Скопировать неделю», отметка «Выполнено».
- **Таблицы** — локальные таблицы с живой формулой `=SUM(...)` / `=AVERAGE(...)`,
  редактирование ячеек двойным кликом или с клавиатуры (Enter/Tab/Escape),
  формульная строка, агрегаты по дням.
- **План** (3-2-1 / план на завтра) — задачи с приоритетами, чекбоксы,
  «Перенести невыполненные на завтра», свои элементы можно перетаскивать.
- **Отмена (Ctrl/Cmd+Z)** — история последних действий (до 20) прямо в памяти;
  у каждого действия также есть тост с кнопкой **«Отменить»** (~5 с).
- **Синхронизация между устройствами** — вход в кабинет и перенос данных в
  Supabase: изменения уходят сами, снимается «побеждает более свежая запись»,
  удаление не воскресает. Разбор — в разделе «Синхронизация».

## Стек

- React 18 + TypeScript + Vite
- Zustand (состояние), Dexie (IndexedDB), dexie-react-hooks
- @dnd-kit/core + @dnd-kit/sortable (drag & drop), framer-motion (анимации)
- sonner (тосты), lucide-react (иконки), Tailwind CSS v4, PWA (Workbox)
- Electron 44 + electron-builder (десктопная версия `.exe`)

## Команды

```bash
npm install             # установить зависимости
npm run dev             # дев-сервер (http://localhost:5173)
npm run build           # продакшен-сборка в dist/ (для Electron, база /)
npm run build:web       # сборка для публикации: префикс сайта + проверка манифеста
npm run verify:manifest -- /Momentum/   # проверить уже собранный dist
npm run preview         # локальный предпросмотр сборки
npm run icons           # перегенерация иконок PWA
npm run qr -- <адрес>   # перегенерация QR-кода со ссылкой на приложение
npx tsc -b --force      # проверка типов

npm run electron:dev    # окно Electron поверх дев-сервера (HMR работает)
npm run electron:start  # окно Electron поверх собранного dist/
npm run electron:build  # установщик .exe и portable-версия → release/

npm run release:status  # текущая версия и список опубликованных релизов
npm run rollback -- plan  --to 1.0.0   # что откатится, ничего не меняя
npm run rollback -- run   --to 1.0.0 --yes   # откатить и закоммитить
```

## Запуск

1. **В браузере**: `npm run dev` и откройте `http://localhost:5173`.
2. **Как приложение с иконкой на рабочем столе** (без .exe) — в самом приложении
   есть кнопка установки: баннер на дашборде и раздел **«Приложение»** в настройках.
   Chrome, Яндекс.Браузер и Edge покажут системный промпт (проверено на
   Яндекс.Браузере 26.8), Android — диалог установки, iOS — пошаговую подсказку
   («Поделиться» → «На экран “Домой”»). Если промпт недоступен или пользователь
   его закрыл, в настройках остаётся кнопка «Как установить» с точными шагами.
3. **Как обычная программа `.exe`**: `npm run electron:build`, затем запустить
   `release/Momentum-1.0.1-x64-setup.exe` — установщик создаст ярлык на рабочем
   столе и в меню «Пуск». Без установки: `release/Momentum-1.0.1-portable.exe`.

### Десктопная версия (Electron)

- Приложение открывается отдельным окном без адресной строки, с русским меню
  (Приложение / Правка / Вид / Окно / Помощь) и сохранением размера и позиции окна.
- Статика отдаётся встроенным сервером на `127.0.0.1` (случайный порт), а не через
  `file://` — так продолжают работать Service Worker, офлайн-кэш и ES-модули.
- Данные лежат в `userData` (IndexedDB) и переживают перезапуск; пункт меню
  «Папка данных» открывает её в проводнике.
- Окно создаётся с `contextIsolation`, `sandbox`, без Node-интеграции; доступ к
  Electron ограничен мостом `window.momentumDesktop` из `electron/preload.cjs`.
- Собранная страница отдаётся с CSP и `X-Content-Type-Options: nosniff`.
- Ярлыки из манифеста (`?section=habits|workouts|dayplan`) открывают нужный раздел,
  текущий раздел тоже сохраняется в адресной строке.

## Публикация: сайт, телефон, Windows

Три адреса, три способа доставки. Всё публикуется из одного репозитория.

| Что | Где | Как |
| --- | --- | --- |
| Веб-версия | `https://<владелец>.github.io/<репозиторий>/` | `pages.yml`, сама при пуше в `master` |
| Страница загрузки | `…/download.html` | там же, вместе с сайтом |
| Windows `.exe` | GitHub Releases | `release.yml`, вручную с флажком **publish** |

### Сайт на GitHub Pages

Workflow собирает фронтенд с префиксом `/<имя репозитория>/` — страница
проекта на Pages лежит в подкаталоге, а не в корне домена. Без префикса сборка
проходит успешно и публикуется нерабочей: пустые файлы, нет иконок, service
worker отдаёт 404. Поэтому префикс не «просто настроен», а проверяется
**после** сборки — `scripts/verify-manifest.mjs` (15 проверок) смотрит на
готовый `dist/`:

```bash
npm run build:web              # сборка + проверка, локально
npm run verify:manifest -- /Momentum/   # проверить уже собранный dist
```

Префикс, адрес приложения и ссылка на релиз подставляются из имени
репозитория (`scripts/build-web.mjs`). Держать `/Momentum/` вручную в трёх
местах — значит гарантированно забыть про одно из них.

**Что ещё пришлось учесть при переносе в подкаталог:**

- `id`, `start_url`, `scope` манифеста и `navigateFallback` service worker'а
  обязаны начинаться с префикса, иначе браузер не предложит установку;
- пути в `index.html` идут через `%BASE_URL%`, абсолютные не найдутся;
- `connect-src` в CSP дополняется адресом Supabase **на сборку**: без
  `VITE_SUPABASE_URL` в политике остаётся только `'self'`; читать его оттуда
  надо через `loadEnv`, а не `process.env` (см. дефекты ниже);
- в `dist` кладётся `.nojekyll` — иначе Jekyll на Pages вырежет служебные
  файлы, нужные обновлению приложения.

### Установка на телефон

Мобильная версия — это тот же PWA: он уже отвечает всем требованиям установки
(`display: standalone`, иконки 192/512, maskable, monochrome для badge,
service worker с precache). Отдельной сборки `.apk` нет и не требуется.

Страница `download.html` показывает **QR-код** со ссылкой на приложение —
навести камерой на монитор быстрее, чем вводить адрес с клавиатуры телефона.
QR лежит в git как SVG и генерируется скриптом, а не вручную:

```bash
npm run qr -- https://<владелец>.github.io/<репозиторий>/
```

Подсказки на странице различают платформы: Android — меню `⋮` →
«Установить приложение», iOS — «Поделиться» → «На экран “Домой”». Это ровно
те подсказки, которые `usePwaInstall` показывает в самом приложении, когда
браузер не присылает `beforeinstallprompt`.

### Релизы и откат

Публикация `.exe` **никогда не запускается сама**: вкладка Actions →
**Run workflow**, и только с дополнительным флажком **publish**. Без него
сборка просто сохраняется артефактом на 14 дней.

В релиз попадают два файла: установщик `Momentum-<версия>-x64-setup.exe` и
переносимая `Momentum-<версия>-portable.exe` без установки. Плюс служебные
`latest.yml` и `.blockmap` — их читает `electron-updater`, без них автообновление
не работает, поэтому в релизе они обязательны, даже если пользователю не видны.

- Файлы: `Momentum-1.0.0-x64-setup.exe` (107 МБ), `Momentum-1.0.0-portable.exe`

- Установщик **не подписан**, поэтому Windows при первом запуске покажет
  «Неизвестный издатель» — это нормально для сборки без сертификата.

Три дефекта, найденных при первом выпуске, уже исправлены в workflow:

1. В шаге проверки кабинета остался bash-синтаксис, а job собирается на
   `windows-latest`, где оболочка по умолчанию — PowerShell. Шаг падал вместо
   предупреждения. Лечится `shell: bash` (добавлено и в `release.yml`, и в
   `pages.yml`).
2. Шагов сборки было два, и при `publish=true` выполнялись оба: получались два
   черновика с одним тегом `v1.0.0`, причём `latest.yml` и установщик оказывались
   в разных релизах, а скачивание такое не находит. Теперь сборка одна на запуск.
3. `releaseType: release` в `package.json`: по умолчанию релиз остаётся
   **черновиком**, а черновик не виден в `releases/latest`, на который ведут
   кнопки страницы загрузки.

Про первый прогон `electron-builder` стоит сказать отдельно: он упал с 422
(«Published releases must have a valid tag»), и это **не** «в репозитории не было
тега», как выглядело сначала. Настоящая причина — гонка.

electron-builder держит кэш publisher'ов по конфигурации публикации. На две цели
(`nsis` и `portable`) publisher'ов получается два, каждый создаёт релиз сам, и в
лог идёт **две** строки `creating GitHub release`. Первый POST создаёт релиз и
тег, второй приходит следом и получает 422 — релиз с таким тегом уже есть.
Хуже всего, что проигравший отменяет свои загрузки: на первом прогоне 1.0.1 релиз
остался с одним `.blockmap`, на втором — без него, то есть без файла, который
`electron-updater` читает, чтобы качать обновление частями.

Поэтому публикует ровно одна цель:

```bash
npx electron-builder --win nsis     --publish always   # релиз, установщик, blockmap, latest.yml
npx electron-builder --win portable --publish never    # только сборка
gh release upload v<версия> release/Momentum-*-portable.exe --clobber
```

Тег workflow всё равно создаёт заранее (`v<версия>` на текущем коммите): релиз
должен указывать ровно на тот коммит, из которого собраны файлы.

Ещё ловушка того же electron-builder: если релиз опубликован **больше двух часов
назад**, он больше не догружает в него файлы — в `gitHubPublisher` стоит отказ
«existing release published more than 2 hours ago», и публикация молча
пропускается. Забытый `.blockmap` спустя два часа уже не допочинить, нужен
новый номер версии.

### Почему откат идёт вперёд, а не назад

`electron-updater` сравнивает версии и **не предлагает downgrade**. Если человек
уже стоит на сломанной 1.0.1, «вернуть ему 1.0.0» технически невозможно. Поэтому
откат устроен так же, как у Chrome и VS Code — отменённый код выпускается новым
номером, и обновлятор приходит к нему штатно.

### Порядок действий

```bash
npm run release:status                  # 1. понять, что сломан
npm run rollback -- plan  --to 1.0.0    # 2. посмотреть план: версия и отменяемые коммиты
npm run rollback -- run   --to 1.0.0 --yes   # 3. откатить и закоммитить
```

`run` сам отменяет коммиты сломанного релиза (`git revert`, без переписывания
истории — репозиторий публичный), поднимает версию выше всех занятых и создаёт
коммит. Дальше остаётся руками:

```bash
gh release delete <плохой-тег> --yes   # отозвать плохой релиз
git push                              # отправить откат
```

и опубликовать через **Actions** с флажком **publish**.

Скрипт отказывается работать, если есть незакоммиченные правки, и требует
явного `--yes`. Цель `--to` принимает и версию, и тег, и любой git-реф.

### Как обновляется приложение

Обновление **автоматическое**, но публикация релиза остаётся ручной.

**Десктопная версия (`.exe`).** Программа сама спрашивает GitHub Releases при
запуске и затем раз в 6 часов, новая версия скачивается в фоне, а
устанавливается при закрытии программы. Поставить её раньше можно тремя
способами:

- кнопка **«Обновить»** в карточке «Обновление» на экране «Профиль»
  (вкладка «Настройки»);
- действие **«Обновить»** в тосте «Обновление готово»;
- пункт **«Перезапустить и обновить»** в меню **Momentum** (активен, когда
  обновление уже скачано).

Состояние скачивания живёт в главном процессе, поэтому перезагрузка окна
(`Ctrl+R`) его не теряет. Проверка версии сравнивает числа, а не подстроку:
`1.0.1` и `1.0.10` больше не путаются.

**PWA и веб-версия.** Service Worker зарегистрирован с `registerType: 'autoUpdate'`,
поэтому новая версия подхватывается сама при следующей загрузке. Кнопка
**«Обновить сейчас»** в том же разделе применяет обновление не дожидаясь
следующего открытия.

**Что нужно для проверки.** Пока релиз не опубликован, обновляться нечему:
`electron-updater` берёт версии из GitHub Releases. Первая проверка реального
обновления возможна только после публикации 1.0.0 и сборки 1.0.1.

## Знак и иконки

Знак — сквиркл 512×512 с сегментным кольцом: восемь дуг, `r=142`, обводка 38,
торцы скруглённые, шаг `62 / 49.53`. Градиент `#7C5CFF → #6B84FF → #4A8CFF` идёт
строго снизу-слева вверх-вправо. Кольцо занимает 63% ширины и укладывается в
safe zone 80%, поэтому маска Android знак не срезает.

Исходники лежат в `public/icons`:

| файл | назначение |
| --- | --- |
| `momentum-logo.svg` | основной знак, тёмная подложка `#0A0C12` |
| `momentum-logo-light.svg` | светлая подложка — печать и экспорт |
| `momentum-logo-mono.svg` | без подложки, обводка на `currentColor` — badge и CSS |
| `momentum-logo-maskable.svg` | подложка во весь квадрат, кольцо на 63% |

**Сдвиг штриховки — через `stroke-dashoffset`, а не `transform`.** Оба варианта
дают одинаковое расположение дуг, но `transform="rotate(-102.5 256 256)"`
поворачивает и систему координат градиента вместе с элементом: ось уезжает на
102,5°, и вместо «снизу-слева вверх-вправо» получается «снизу-справа
вверх-влево». `dashoffset` двигает только штриховку. Если будете править
исходник — не возвращайте `transform`.

**Зазоры между дугами схлопываются скруглёнными торцами.** По номиналу
`62 / 49.53` дуга занимает 25°, зазор 20°, но торцы добавляют по обводке/2 = 19
единиц с каждого края. В итоге остаётся **≈40,3° дуги и ≈4,7° зазора**. Ширина
зазора при уменьшении знака:

| размер | зазор |
| --- | --- |
| 16 px | 0,36 px |
| 24 px | 0,54 px |
| 32 px | 0,72 px |
| 48 px | 1,08 px |
| 64 px | 1,44 px |

То есть ниже 64 px восемь дуг сливаются в сплошное кольцо — форму держит
силуэт сквиркла, а не разрывы. Это осознанный размен: кольцо на 16 px всё равно
не может показать восемь зазоров (окружность 27,9 px, на восемь зазоров — 3,5 px
каждый). Если разрывы нужны и на малых размерах, уменьшайте `stroke-dasharray`
и пересобирайте — но тогда и `verify-icons.mjs` придётся обновить, он сверяет
видимую длину дуги.

**Пересборка и проверка.** Обе операции требуют `sharp`, который ставится
разработчиком и намеренно не входит в `package.json` — в CI и в сборке
приложения он не участвует:

```
npm i -D sharp
node scripts/build-icons.mjs    # SVG → PNG-набор
node scripts/verify-icons.mjs   # 31 проверка по пикселям
```

**Favicon собран из основного знака, а не из моно-версии.** Favicon грузится
как отдельный документ и не наследует `color` страницы, поэтому белый силуэт
на прозрачном фоне на светлой панели вкладок просто исчез. С тёмной подложкой
знак читается на любом фоне. Моно-файлы `badge-192.png` / `badge-512.png`
оставлены для badge уведомлений (Android рисует его однотонным силуэтом — цветную
иконку туда скармливать нельзя) и объявлены в манифесте с `purpose:

вшитый в `.exe`, совпадает с `public/icons/icon-512.png` (расхождение 0,1 при

машине приложения; сайт отдаёт те же файлы, SHA совпадает с локальными. Старую
картинку в этом случае держит кэш, а не сборка:

- **Windows.** Обновление поверх установленной копии меняет `Momentum.exe`, но
  оболочка продолжает показывать знак, который уже видела по этому пути.
  Обновление кэша: перезапуск проводника (`taskkill /f /im explorer.exe` и
  запуск заново — проводник поднимется сам) либо удаление с переустановкой.
  Значок на панели задач обновляется после перезапуска проводника.
- **Установленное приложение с телефона (PWA).** Иконка закрепляется при
  установке и дальше не перечитывается, сколько бы манифест ни менялся: новый
  знак появится только после удаления и повторной установки.

Оба случая — не дефект сборки, поэтому «обновить логотип» в исходниках не
помогает: там уже тот знак, который вы хотите видеть.

## Профиль и кабинет

Экран в интерфейсе называется **«Профиль»**; «личный кабинет» — это только
название серверной части в документации. Отдельной вкладки внизу нет: на
телефоне нижняя панель остаётся из пяти пунктов, а профиль открывается из
аватара в правом верхнем углу. Шестерёнка в шапке ведёт в тот же экран.

Порядок секций: шапка (аватар, имя, строка о хранении данных, чипы) → пять
метрик → вкладки **Аккаунт · Настройки · Данные · Опасная зона**.

**Аватар** — монограмма на бренд-градиенте, один `div` со
`linear-gradient(135deg,#7C5CFF,#4A8CFF)`, скругление 30%. Ни SVG, ни загрузки
файла: монограмма всегда состоит из букв. Это кнопка с поповером,
`aria-current` ей не нужен, а `aria-haspopup` / `aria-expanded` проставляет
общий `Popover`. Поповер закрывается по `Esc` и клику вне, фокус возвращается
на кнопку; при `prefers-reduced-motion` всё появляется мгновенно.

**Имя профиля** лежит одной записью в существующем хранилище настроек
(`settings.profileName`), поэтому схему Dexie ради одного текстового поля менять
не пришлось. Поле защищено от глобального `Ctrl/Cmd+Z`: перехват отмены срабатывает
только если фокус не в `INPUT` / `TEXTAREA` / `contenteditable`.

**Градиент** встречается ровно в двух местах: аватар в шапке профиля и кнопка
**«Экспорт · JSON»** — единственная кнопка с градиентом в секции «Данные».
Остальное — `#1A1F2B` с границей `#262B38`.

**Опасная зона** — отдельная красная плашка с двойным подтверждением.

### Личный кабинет (Supabase)

Четыре потока: **вход**, **выход**, **восстановление пароля** по ссылке из письма
и **смена пароля** на живом аккаунте. Смена требует повторного входа текущим
паролем (`signInWithPassword`) перед `updateUser` — иначе пароль смог бы сменить
любой, у кого на устройстве осталась открытая сессия.

Всё это работает поверх Supabase Auth. Логика — в `src/store/authStore.ts`,
подключение — в `src/lib/supabase.ts`. Ключи лежат в `.env.local` (в git не
попадает), шаблон — `.env.local.example`:

```
VITE_SUPABASE_URL=...
VITE_SUPABASE_ANON_KEY=...
VITE_SUPABASE_REDIRECT_URL=http://localhost:5173/
```

основного пароля Яндекса указывается **пароль приложения**.

«Аккаунт» объясняет, что делать, и не рисует кнопок входа — приложение
продолжает работать полностью локально. Авторизация не должна быть условием
работы программы.

Схема Postgres — `supabase/schema.sql`, её нужно применить в SQL Editor.
Подробности (зеркало репликации, `momentum_push` / `momentum_pull`, слияние по
`updated_at`) — в разделе «Синхронизация» ниже.

## Синхронизация

Появилась в 1.0.1. Вход в кабинет был и раньше, но переноса данных между
устройствами не было.

### Как устроено

На сервере нет таблиц под каждый тип данных. Есть одна таблица
`public.momentum_rows`: `(user_id, table_name, row_id, payload jsonb,
updated_at, deleted_at)`. Это **зеркало реплики**, а не модель запросов — движок
отправляет сюда изменённые записи и забирает чужие. Добавление поля в TS-тип
не требует миграции SQL.

Две функции:

- `momentum_push(rows jsonb)` — сливает пачку. На конфликте побеждает более
  свежая запись, старая отбрасывается. Метка зажимается сверху
  `least(updated_at, now() + interval '1 hour')`: часы устройства могут уплыть
  вперёд, и такая метка иначе захватила бы разрешение конфликтов у всех.
- `momentum_pull(since_seq, limit_rows)` — отдаёт изменения после курсора,
  батчами.

`security_definer = false`, RLS включён — политики действительно применяются.
`execute` отозван у `public` и у `anon`: у `momentum_push` был явный грант роли
`anon`, который один `revoke from public` не снимает (видно в `pg_proc.proacl`).
Без входа в аккаунт ни отправка, ни приём не проходят.

### Курсор приёма — `seq`, а не метка времени

Первая версия курсором считала `updated_at`. Это неверно: **вся пачка одного
запроса получает одно `now()`**, и строки, попавшие на границу батча, терялись
навсегда. Курсор переведён на порядковый номер `seq`.

Вторая ошибка была в самом `seq`. Он был объявлен
`bigint generated always as identity` — то есть номер выдавался **один раз, при
вставке**. Ветка `on conflict … do update` его не трогала, и получалось так:

```
устройство А создаёт привычку           → seq = 100, А запоминает курсор 100
устройство Б переименовывает её позже   → seq остаётся 100
устройство А тянет изменения после 100  → правку не видит никогда
```

Строка не «приезжает второй раз» — она навсегда остаётся позади курсора. Пока
обмен шёл только свежими записями, это не проявлялось: правка на втором
устройстве просто не доезжала. Теперь `seq` — обычный `bigint` с default из
именованной последовательности, а ветка конфликта двигает его через `nextval`.
Лечится `supabase/003-seq-on-update.sql`.

### Как движок узнаёт об изменениях

Через хуки Dexie `creating` / `updating` / `deleting` (`src/db/syncHooks.ts`).
Существенная оговорка: **низкоуровневая запись через `indexedDB` /
`objectStore.put` эти хуки не вызывает** — движок просто не узнает об
изменении. Это не теория: запись напрямую в `objectStore` была проверена, и
`momentum_push` так и не позвали. Значит любая проверка отправки обязана идти
через интерфейс приложения, а не через базу.

Журнал удалений (tombstones) лежит в `localStorage`, а не в IndexedDB: хук
`deleting` выполняется внутри уже открытой транзакции IDB, и записать туда
нельзя. Сброс устройства журнал не чистит — локально удалённая запись должна
уехать в облако, иначе вернётся обратно.

### Планировщик

Порядок обмена — **сначала push, потом pull**. Локальная правка ставит
отложенный запуск 1,5 с; полный обмен — по событию возврата в сеть
(`online`), при уходе вкладки с экрана (`visibilitychange`) и раз в 5 минут.
Цикл не накладывается на себя: параллельный запуск ставится в очередь.

### Решения человека

Если на устройстве уже есть данные, а в облаке тоже, приложение спрашивает:
**«Отправить данные устройства в облако»** или **«Взять данные из облака»**.
Пока владелец данных не выбран, обычный обмен не идёт — иначе устройство либо
затёрло бы чужие данные, либо молча слило два аккаунта в один.

### Как это проверено

- **Сервер, 29 проверок на живом JWT** — права, push/pull, целостность
  `payload`, строгий рост `seq`, граница батча, LWW, tombstone с чисткой
  `payload`, зажим метки, изоляция аккаунтов, потолок `limit`, и отдельная
  регрессия «правка видна за уже отданным курсором».
- **Браузер, 28 проверок на живом движке** — вход, диалог выбора, создание
  привычки интерфейсом (хук → `momentum_push` → строка в облаке с целым
  `payload`), приём более свежей облачной версии, удаление категории интерфейсом
  → tombstone с пустым `payload`, опоздавшая правка не воскрешает строку,
  повторный обмен ничего не меняет.

Предупреждение: до релиза переноса между настоящими устройствами не было.
Проверка шла в одном браузере, где «второе устройство» — это прямой вызов
`momentum_push` от имени того же пользователя. Настоящий сетевой обмен между
двумя телефонами не проходился.

## Данные (экспорт/импорт, сброс)

- Все данные живут в IndexedDB браузера и сохраняются между сессиями.
- Внутри приложения доступны действия **«Экспорт · JSON»** (скачивает файл) и
  **«Импорт»** (загружает JSON обратно) на экране «Профиль», вкладка «Данные».
- Полная очистка — вкладка «Опасная зона» на том же экране, с двойным
  подтверждением. Вне приложения — очистка данных сайта в настройках браузера.

## Проверки

Сквозные сценарии (приложение + IndexedDB как источник истины) проверены для:

**Привычки**
1. Отметка привычки кольцом → тост + **Отменить** → лог убран из БД.
2. Пропуск дня (с причиной «Болезнь») → серия не прерывается, ячейка тепловой
   карты отмечается как пропуск.
3. 2 пропуска подряд → серия сбрасывается, показывается тост
   «Серия прервалась — начнём заново?».
4. Перетаскивание привычки между категориями/подкатегориями → категория в БД
   обновляется, доступен undo (перенос обратно или «Отменить»).
5. Ctrl/Cmd+Z (и русская раскладка) откатывает действия, история ограничена 20
   действиями; при пустой истории — «Отменять нечего».

**Тренировки**
6. Создание тренировки «Грудь + трицепс» с упражнением «Жим лёжа» 3×12×60 —
   запись и упражнение подтверждены в БД.
7. «Скопировать неделю» в 2026-09-28 — создана копия тренировки с новым
   `workoutId` и копией упражнения, тост «Неделя скопирована. Перенесено тренировок: 1».

**Таблицы**
8. Формулы `=SUM(A1:A3)` → 60, `=AVERAGE(B1:B3)` → 2, `=MAX/MIN/COUNT/IF`,
   ссылка `=A1*2` → 20. Живой пересчёт: изменение A2 20 → 25 обновило A4 60 → 65.
   Формулы и значения сохранены в БД как `raw`.

**План 3-2-1**
9. Добавление пунктов в три блока, чекбокс (тост + «Отменить»), кольцо прогресса 25 % (1 из 4).
10. DnD между блоками и перестановка внутри блока, оба действия попадают в историю
    и откатываются по Ctrl+Z.
11. «На завтра» — 3 невыполненных пункта перенесены на 2026-09-26, тост
    «Перенесено: 3», откат возвращает их на 2026-09-25.

**Мобильный прогон** (эмуляция узкого вьюпорта 390×844 и 360×640 + touch-события)
12. Sidebar скрыт, нижняя навигация видна (5 пунктов 70×53), горизонтального
    переполнения страницы нет ни в одном разделе; таблица скроллится внутри себя,
    неделя — в одну колонку.
13. Свайп влево по карточке → меню пропуска; долгое нажатие (480 мс) → меню пропуска.
14. Touch-dnd: перенос привычки между подкатегориями и перенос пункта плана

## Исправленные в ходе проверок дефекты

- `seq` выдавался один раз, при вставке, и ветка `on conflict … do update` его
  не двигала. Правка существующей строки навсегда оставалась за уже отданным
  курсором, то есть не доезжала до других устройств **никогда**: не работало
  даже переименование привычки на втором телефоне. Пока обмен шёл только
  свежими записями, дефект не проявлялся. Исправлено `003-seq-on-update.sql`;
  при переносе колонка намеренно не `identity`, а `bigint` с default из
  именованной последовательности.
- Собственная ошибка при исправлении: шаг `alter column … drop identity`
  **удаляет и свою последовательность**, а `create sequence if not exists` шёл
  перед ним и молча ничего не делал. Default и ветка конфликта ссылались на
  несуществующее имя (`42P01`), а при обходе через `setval` номера строк уехали
  назад — за уже розданные курсоры. Порядок теперь: сначала `drop identity`,
  потом `create sequence`, потом `setval` над текущим максимумом, и лишь затем
  перенумеровывание строк.
- `vite.config.ts` брал адрес Supabase из `process.env` — на локальной сборке
  он там отсутствует, и в CSP оставался `connect-src 'self'`, который блокировал
  всю синхронизацию. Сборка проходила успешно, внешне всё выглядело исправным.
  Переведено на `loadEnv`; локальная сборка теперь даёт
  `connect-src 'self' https://blivexnftddazmsxjzbq.supabase.co`.
- Одна неполная запись привычки роняла весь раздел: рендер падал на
  `frequency.type`, React выкидывал поддерево целиком, и привычки не было видно
  вообще — при полной базе. Теперь такие записи отбрасываются при загрузке
  стора с предупреждением в консоли. Проверено: битая строка из старой версии
  или из неполной выгрузки больше не делает раздел пустым.
- `revoke execute … from public, anon` для `momentum_push` снимал права не
  полностью: у функции был явный грант роли `anon`, и одного `revoke from
  public` недостаточно. Отзыв делается раздельно, результат сверяется через
  `pg_proc.proacl`.

- **Вкладки не переключались вообще — ни одна, включая «Дашборд»:** ползунок
  меню дёргался туда-обратно и раздел оставался прежним. Две ошибки в одном
  месте, `src/lib/deepLink.ts`. Первая: событие `navigate` Навигационного API
  прилетает и на **наш собственный** `history.replaceState`, которым
  `rememberSection` пишет `?section=` в адрес. Вторая: обработчик читал
  `window.location.search`, а на момент `navigate` адрес **ещё старый** — новое
  значение лежит в `event.destination.url`. Вместе это замкнуло петлю: клик
  пишет `?section=habits` → подписка видит пустой адрес и ставит `dashboard` →
  эффект снова пишет адрес → подписка снова читает старое. На пять кликов
  получалось 201 `replaceState`, а раздел не менялся ни разу. Замечено
  пользователем как «перетаскивает и не открывается», найдено перехватом
  `replaceState` и `navigate` через CDP **до** кода приложения
  (`Page.addScriptToEvaluateOnNewDocument`): перехват после маунта не видит
  стартовую запись адреса и петлю не показывает. Исправлено: обработчик берёт
  адрес из `destination.url` и молчит, если переход ведёт ровно туда, куда мы
  записали сами; `rememberSection` не пишет адрес, если он уже верный. Проверка
  `npm run check:tabs` (проверка 41) падает на старом коде и проходит на новом.

## Заметки по разработке

- Драг-анимация карточки привычки реализована через обычный `div` (не
  `motion.div`): framer-motion «съедал» transform от dnd-kit, из-за чего карточка
  не следовала за курсором.
- История действий — in-memory (не в IndexedDB), поэтому откат доступен только
  в текущей сессии; ограничение 20 действий настраивается в настройках. Импорт и
  сброс данных очищают историю, чтобы откат не воскресил удалённые записи.
- Тост «Отменить» связан с той же историей: клик по нему выполняет откат
  конкретного действия; 5-секундным ограничением задан только показ тоста.
- Отмена тренировки восстанавливает запись по исходному индексу в weekly plan и не
  трогает БД, если этот `id` уже снова присутствует (например, после отката другой
  истории).
